## Оценка пути команды (кратко)
- Отдельные лимиты на чтение и обработку медиа + повтор — согласен. Публичное чтение готового JPEG не должно стоять в общей очереди с перекодированием. Ответ 503 должен быть не JSON на `<img>`, а повтор с задержкой; в интерфейсе — заглушка той же пропорции «Фото не загрузилось · Повторить». Риск: повтор без ограничения создаёт шторм запросов — нужно не больше 2 попыток и задержка с разбросом.
- Использовать существующий API доступа к поставщику вместо sessionStorage и simulateApproval — согласен. Блокер: CatalogAccessRequestDialog (для каталога, без поставщика) не имеет supplierId. Значит, либо запрос из каталога превращается в запрос по конкретному поставщику, либо диалог убираем из потока. Создавать «общий доступ» без серверного объекта нельзя.
- Конкретный оффер → настоящий запрос (inquiry); поиск без результатов → не придумывать offerId — согласен. Поиск без результатов остаётся отдельным «Запросом на подбор» только если у него есть свой серверный объект; если его нет — убрать кнопку, а не имитировать.
- Сообщения внутри существующего запроса, без дубля CRM — согласен. Блокер: ответ продавцу нельзя давать без проверенной личности и правил архива. Сейчас email не подтверждён ⇒ показываем состояние, а не кнопку.
- termId владеет ценой/валютой/оплатой/ступенями/местом — согласен, это главный риск данных: CIF EUR сейчас показывает ступени FOB CNY и T/T. Без привязки к termId никакой текст это не исправит.
- Документы: «нет данных» вместо mock true — согласен. Категорию по способу вылова не выводить как факт.
- Пустые кнопки удалить или подключить — согласен; «Профиль поставщика» подключить ссылкой, «Шортлист» и «Сравнить» скрыть.
- Галерея на Radix Dialog с возвратом фокуса на миниатюру, открывшую её, — согласен.
- Мобильный порядок: полный заголовок и публичные факты до фото, короткая закреплённая кнопка — согласен.
- Нагрузка 10 000: только задокументировать профиль и план проверки; не писать «проверено».

## Два разных действия — имена не пересекаются

| Смысл | RU | EN | ES |
|---|---|---|---|
| Доступ, кнопка | Запросить доступ к цене | Request price access | Solicitar acceso al precio |
| Доступ, ожидание | Отправляем запрос доступа… | Sending access request… | Enviando solicitud de acceso… |
| Доступ, успех | Запрос доступа отправлен. Цена и данные поставщика откроются после одобрения. | Access request sent. Price and supplier details open after approval. | Solicitud de acceso enviada. El precio y los datos del proveedor se mostrarán tras la aprobación. |
| Доступ, уже есть | Доступ ожидает решения поставщика | Access awaiting supplier decision | Acceso pendiente de decisión del proveedor |
| Доступ, ошибка | Не удалось отправить запрос доступа. Повторить | Couldn't send access request. Retry | No se pudo enviar la solicitud de acceso. Reintentar |
| Запрос, кнопка | Отправить закупочный запрос | Send purchase inquiry | Enviar consulta de compra |
| Запрос, заголовок окна | Закупочный запрос по предложению | Purchase inquiry for this offer | Consulta de compra sobre esta oferta |
| Запрос, ожидание | Отправляем запрос… | Sending inquiry… | Enviando consulta… |
| Запрос, успех | Закупочный запрос отправлен · №{short}. Это не заказ и не оплата. | Purchase inquiry sent · No. {short}. This is not an order or payment. | Consulta de compra enviada · N.º {short}. No es un pedido ni un pago. |
| Запрос, не подтверждён | Ответ сервера не получен. Проверяем, сохранён ли запрос… | No server response. Checking whether the inquiry was saved… | Sin respuesta del servidor. Comprobando si se guardó la consulta… |

Правило: после «не подтверждён» не отправлять повторно, а читать запрос по idempotency-ключу; кнопку повторной отправки показывать только если запрос не найден.

## Поля окна запроса
- Количество* — ошибка: «Минимум {moq} {unit}» / «Minimum {moq} {unit}» / «Mínimo {moq} {unit}».
- Базис* — выбор termId; при смене меняются цена, валюта, оплата, ступени. Если вариант один, показать текстом, а не списком.
- Сообщение* — ошибка: «Опишите требования к поставке» / «Describe your supply requirements» / «Describe sus requisitos de suministro».
- Звёздочка с подписью «* обязательно» / «* required» / «* obligatorio»; у каждой ошибки aria-describedby; при отправке фокус на первом ошибочном поле; закрытие окна возвращает фокус на кнопку, которая его открыла.

## Переписка: компактная анатомия
Продавец, входящие (строка списка): товар · количество + базис · компания покупателя · время · статус. В деталях — сообщения по порядку, без UUID; квитанция короткая, с копированием.
Состояния ответа:
- нет проверенного email: «Ответ недоступен: подтвердите email компании» / «Reply unavailable: verify company email» / «Respuesta no disponible: verifique el email de la empresa» — со ссылкой на существующую проверку, если она есть; иначе без ссылки.
- можно ответить: поле «Ответ покупателю» + «Отправить ответ» / «Reply to buyer» · «Send reply» / «Responder al comprador» · «Enviar respuesta».
- отправка / ошибка / неподтверждённый результат — по тем же правилам, что и у запроса.
Покупатель: в квитанции и в «Мои запросы» — «Ответов пока нет» / «No replies yet» / «Aún no hay respuestas»; появившийся ответ показывается в той же ленте. Никаких «скоро ответит», телефонов, email и выдуманных контактов.

## Единицы и значения
- Температура: формат «−18 °C» только если источник явно хранит единицу (или контракт её фиксирует); иначе показать значение как есть + «единица не указана». Не добавлять °C вслепую.
- «Годен до: 09.2027», «Произведено: 09.2026» (формат месяца по языку интерфейса); «Срок годности» использовать только для длительности.
- Справочные значения (wild, BQF, разделка, упаковка) — переводить по словарю; неизвестный ключ — показать как есть, не скрывать. Проверка — по полям справочника, а не «нет кириллицы на странице»: названия продавца, латинские имена, Incoterms и порты законно могут быть на любом языке.
- Документы без подтверждения: «Нет данных» / «Not provided» / «Sin datos», без зелёных галочек.
- Страны: «Происхождение» и «Страна поставщика» — две подписи.

## Мобильная иерархия и фокус (390px)
- Порядок: полный заголовок (переносится, до 200 символов, без обрезки) → строка публичных фактов (вид, форма, происхождение, базис, MOQ, цена или её состояние) → галерея → условия → поставщик.
- Плашка регистрации: одна строка с ссылкой, без фиксированной высоты.
- Закреплённая кнопка: «Создать аккаунт покупателя» / «Create buyer account» / «Crear cuenta de comprador»; перенос разрешён, ширина max = экран − 32px, нижний отступ страницы = реальной высоте панели (через измерение, а не жёсткое число). Сейчас текст 386px > 366px — короткое имя это решает.
- Галерея: фокус внутри окна, Esc/X закрывает, фокус возвращается на открывшую миниатюру; стрелки с подписями; 44px — правило проекта.

## Приёмка (каждый пункт проверяется вручную, скриншоты)
1. Три фото открываются параллельно: нет ORB; при искусственном отказе — заглушка той же пропорции и «Повторить», не более 2 автоповторов.
2. Запрос доступа создаётся только через сервер; после перезагрузки статус читается с сервера; sessionStorage/simulateApproval нигде в потоке.
3. Тексты доступа и закупочного запроса не совпадают ни одной фразой; квитанция запроса содержит товар, количество, базис, номер.
4. Отправка с количеством ниже MOQ и пустым сообщением: 2 отдельные ошибки, фокус на количестве.
5. Fixture с двумя базисами: при выборе CIF EUR не видно ступеней CNY и T/T от FOB.
6. Квалифицированный покупатель: кнопок без действия ноль.
7. Продавец без проверенного email видит объяснение, а не кнопку ответа.
8. Документы без подтверждения показывают «Нет данных».
9. 390×844: заголовок и строка фактов до фото; кнопка не обрезана в RU/EN/ES; ширина документа не превышает экран.
10. Новый запрос создаётся только синтетическим QA-аккаунтом с явной меткой; оффер Mackerel и старый запрос не меняются.
