# Yorso Adversarial Test Review Pilot

Use this experimental skill only as an independent second pass after the normal
Yorso implementation and testing gates have run. Its question is narrower than
"did tests pass?": **would the current tests fail if the promised user-visible
behavior were broken?**

This skill adapts test-review concepts from
`petrkindlmann/qa-skills@b3bb61bd268b147476252c6ed5a0440c87b97441`
under the MIT license. It is not active in a project role until a Yorso Stage B
pilot qualifies it.

## Required Inputs

- Task promise and acceptance criteria.
- Changed production files and complete diff.
- Changed and relevant existing tests.
- Exact test commands and raw results.
- Browser, screenshot, trace or runtime evidence when UI behavior is claimed.

Mark missing inputs as `не проверено`. Never infer a pass from a report alone.

## Review Procedure

1. Build a claim-to-assertion map. For every promised behavior, identify the
   exact test, action and assertion that should fail when the behavior breaks.
2. Read the production diff and tests together. Look for tests that only prove
   rendering, testid presence, helper behavior or mocked implementation detail.
3. Challenge test reliability:
   - conditional assertions or early returns that can skip the proof;
   - swallowed errors, broad catches, forced clicks or arbitrary sleeps;
   - shared mutable state, order dependence or stale fixtures;
   - hallucinated imports, selectors, routes or APIs;
   - weak assertions such as count-greater-than-zero when an exact result is
     required;
   - assertions that repeat data generated by the same implementation under
     test.
4. Challenge boundary coverage. For stateful widgets, include empty, invalid,
   duplicate, second and third consecutive actions, removal, re-add, cancel,
   save and reload where those behaviors are in scope.
5. Run the narrow relevant tests. Repeat unstable or timing-sensitive tests at
   least three times when practical. Record the command and each outcome.
6. When risk justifies it, perform one small mutation probe: temporarily break
   one promised behavior and prove the intended test fails. Revert the probe
   immediately. If no probe was run, say so; never claim mutation coverage.
7. Compare automated evidence with real-flow evidence from
   `yorso-testing-quality-gate-agent`. Do not substitute one for the other.

## False-Green Triggers

Return `NO-GO` when any of the following is true:

- A material claim has no user-observable assertion.
- The relevant test still passes after a narrow break of the claimed behavior.
- A multi-item control is accepted without proving a second consecutive action
  and removal/re-add behavior.
- The test relies only on testids, snapshots or static text while interaction
  behavior is the task.
- Required checks were skipped conditionally or replaced by a mock that cannot
  expose the reported defect.
- The report claims browser, persistence, locale or responsive behavior without
  corresponding runtime evidence.

## Boundaries

- Do not redesign UI or generate a broad replacement test suite.
- Do not duplicate the real-browser acceptance owned by
  `yorso-testing-quality-gate-agent`.
- Do not make release, merge or production-readiness decisions; that remains
  with `yorso-release-reliability-agent` and human approval.
- Do not modify product code while reviewing. A mutation probe must be isolated,
  immediately reverted and absent from the final diff.
- Do not activate this skill in `.agents/manifest.json` role assignments before
  Stage B qualification.

## Output

Answer in Russian with this table:

| Обещанное поведение | Проверяющий тест и assertion | Контрпример / пробел | Вердикт | Требуемый фикс |
|---|---|---|---|---|

Then include:

- `Итог: GO`, `GO WITH RISKS` or `NO-GO`.
- `Команды и результаты:` exact commands and outcomes.
- `Повторяемость:` how many reruns were executed.
- `Mutation probe:` exact probe and failing test, or `не выполнялся`.
- `Не проверено:` missing evidence.
- `Пересечение с действующими skills:` what remains owned by the normal Yorso
  testing and release gates.
